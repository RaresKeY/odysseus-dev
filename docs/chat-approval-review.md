# Exact chat action review

The approval mode chooses who reviews an action. It never enables a disabled tool, adds resource authority, disables confinement or grants elevation. Always Ask uses one exact human decision. Auto-Approve prefers the configured Jev reviewer and permits one independent conversation-model fallback after a technical failure or missing configuration. YOLO skips discretionary review after deterministic admission. New chats and forks start in Always Ask, and changing mode never revives a retired proposal.

Auto-Approve is selectable when either the configured decision endpoint or this conversation's selected model passes configuration admission. Hosted Jev requires its registered credential; compatible local reviewers may be keyless. Missing Jev alone does not disable Auto. Automatic conversation routing checks both assigned model registrations and binds review to the resolved model of the originating turn. No global default or unrelated model is substituted. Readiness makes no inference call and does not establish live endpoint health. If both paths are unavailable, saved Auto remains visible with Always Ask and settings accessible. Activation explains fallback, and a valid denial or uncertainty result is final.

## Independent assessments and deterministic enforcement

`src/approval_policy.py` owns `odysseus-approval-review/v2`, its complete prompt, finite choices, thresholds, reasons and host combiner. `src/approval_review.py` sends one `DecisionRequest` through the existing provider, using `risk_level` as its primary question and `additional_questions` for `user_authorization`, `policy_check` and `effect_scope`. Both supported protocols keep their existing transport. No execution-model completion or browser-action choice is reused as approval.

| Assessment | Values |
| --- | --- |
| Intrinsic risk | low, medium, high, critical |
| Semantic user authorization | unknown, low, medium, high |
| Policy | clear, explicit_restriction, injection, sensitive_egress, credential_probing, security_weakening, destructive_scope, browser_mismatch, insufficient_evidence |
| Effect scope | narrow, broad, unknown |

Authorization concerns the actual target, payload and side effects. An explicitly requested action or its necessary implementation can have high authorization without matching the user's exact syntax. Urgency, agent justification, a broad end goal and retrieved instructions are not grants. Runtime resource access is a separate prerequisite.

Risk concerns effects and current state. An ordinary file write can be low risk even with an already valid elevation grant. Command spelling, `sudo`, an outside-workspace path, sandbox retry or workflow size does not independently determine risk. The policy distinguishes normal authentication from credential probing, traces sensitive derived payloads to their destination, requires authorization for persistent security changes, and evaluates destructive scope and actual browser inputs.

| Risk | Authorization | Host result after valid, confident assessments |
| --- | --- | --- |
| low / medium | any explicit valid label | allow if policy is clear |
| high | medium / high | allow only if policy is clear and scope is narrow |
| high | low / unknown | deny |
| critical | any | deny |

Every policy veto overrides the matrix, including explicit restrictions and injection for low-risk actions. `insufficient_evidence` stops as uncertain. Each required Jev answer must have confidence and selected probability at least 0.95. These are operating thresholds, not calibrated safety probabilities. There is no final model `allow` label that can override the combiner, and no numeric freedom score. Missing, extra, incomplete, nonfinite, non-normalized or contradictory answers fail closed. Provider model identity, primary-answer projection, attempt identity and known usage remain required.

The entire policy fits the existing 4,000-character instruction field. The approval-only `server_user_evidence` contract distinguishes server-provenance authorization evidence from ordinary state. Other decision purposes retain their existing instructions. The prompt version and SHA-256 are recorded; policy is never truncated or assembled from model-controlled text.

## Conversation-model fallback

`src/approval_fallback.py` reuses the existing provider request builders for OpenAI-compatible chat, Anthropic Messages, native Ollama and ChatGPT Subscription Responses. It sends no tools, performs no execution-model answer reuse, caches no approval and retries no provider request. The selected provider receives the same frozen state and semantic policy in a fresh request. Its complete categorical JSON answer contains the four assessment labels and an explicit boolean `uncertain`; it contains no confidence scores or distributions. The host uses the same vetoes/matrix, with uncertainty stopping the action. This separately versioned `categorical_uncertainty/v1` contract does not claim Jev calibration or fabricate probabilities. Both prompt hashes are retained.

A missing/unusable primary or an authentication, transport, timeout or malformed-response failure permits one fallback. A valid denial, low-confidence Jev answer, explicit uncertainty or insufficient-evidence answer never triggers fallback. Accounting/capture failure, cancellation, changed identity or exhausted budget also stops. The review has a shared 60-second maximum: at most half the remaining time for the primary when fallback is possible, and at most 30 seconds for the fallback. Both attempts retain the same cancellation and stale-action checks. Changed saved selection, resolved turn model, action, authorization, resource or policy invalidates approval. An explicitly owner-authorized registered foreground availability fallback retires old cards and increments a review-route revision before rebinding the new originating route. Its bounded server-owned origin lineage is validated against the actual bound route; only a strict extension can change the reviewer for an established outage. Model/request state cannot provide this handoff. In-flight results and already consumed old-route grants cannot cross that revision, including an A-to-B-to-A route cycle.

The generic decision provider still owns durable reservations, TLS validation, no redirects, response-size limits, known usage and settlement. One linked fallback may reserve its own budget after a technically failed primary for the same exact action and policy. Unknown primary usage stays held; it is never changed to zero or treated as unspent. The first linked exemption cannot cover a valid primary outcome, a repeated action/fallback, another unresolved attempt, a usage overrun or a call-count limit; later actions require the separate validated outage-continuation binding. After a technically failed primary and a successfully settled conversation-model review, later exact actions in that run may continue with the same selected reviewer through a narrowly bound outage record. The failed primary is not retried and its unknown usage remains held. Continuations retain the primary configuration, policy/epoch and selected-provider identity (or a bounded, explicit server-owned registered foreground route handoff), reserve each distinct action separately, and obey the original call ceiling. Unrelated unresolved calls, an unresolved fallback, usage overruns and exhausted limits still stop the run. Other decision purposes receive no exemption.

Fallback requires a bound selected/accepted response model contract. Exact documented alias-to-canonical pairs apply only on their official HTTPS origin and path; Google’s `models/` spelling and Ollama’s deterministic default `:latest` spelling remain narrowly supported. It also requires a complete terminal response, valid reported usage and strictly parsed JSON. Tool calls, refusals, truncation and provider model substitution stop it. Native Ollama uses an explicit 16K context with a conservative byte budget covering policy, complete state, framing and output; oversized requests stop before inference. Responses SSE requires one complete terminal event. Unknown or changed alias-to-snapshot substitutions are not guessed; select the explicit provider model ID when the current finite contract cannot bind it. The outgoing selected ID is preserved, and durable activity records the actual reported reviewer ID separately from the pre-dispatch acceptance contract. Anthropic cache creation/read input tokens are included in accounted input usage. Refusals, duplicate JSON keys and truncated responses are rejected on all four adapters. These are offline-qualified adapters, not guarantees that every configured server/model follows the contract; an incompatible model stops Auto with an error. No endpoint-health probing, credential migration or live inference is part of readiness.

## Context and provenance

`src/approval_context.py` reads the authenticated submission chain in owner/chat scope, following stable `previous_submission_id` links rather than guessing transcript roles. Owner-serialized admission assigns a strictly increasing logical timestamp even if wall time moves backward or ties, so predecessor selection cannot skip an intervening accepted ask. Snapshot validation also rejects already disconnected owned rows; it never guesses a replacement order for old branched history. It retains every captured ask in order, including earlier restrictions and later revocations, independently of execution-context trimming. Exact human allow/deny choices are retained as operation fingerprints and source-tagged events in the nullable `ChatAutomationSubmission.approval_evidence` column. These events are evidence, never reusable grants. The startup migration is additive and idempotent; existing submissions and account data remain intact.

The immutable review envelope includes the complete proposed tool input, canonical operation fingerprint, owner/chat/run/submission IDs, policy revision and authority epoch, effective roots and elevation scope, current request authority, effect classification, and sealed filesystem, owned-record, backend, process/job and browser identities. Backend serializers omit credentials. MCP hints retain their server source and untrusted status, including contradictory or missing hints; they do not bypass review. Captured browser target/state and bounded recent tool results are observations, never instructions. Tool errors and omissions remain visible as evidence.

Limits are explicit: 4,096 linked submissions and 24 KiB of user evidence; 32 KiB of total state; 4 KiB of optional observations; at most eight recent tool results with marked 1 KiB field truncation. Complete user evidence and exact action take priority. Above 32 entries, older exact asks and human decisions are packed as an ordered JSON archive, with eight recent entries kept individually. This removes repeated metadata without summarizing or filtering instructions. One bounded owner/chat SQL read replaces one query per predecessor. Every linked ask digest and decision shape is revalidated before and after review and on grant consumption; there is no stale history cache. Overflow or a missing/corrupt chain blocks Auto instead of silently dropping a restriction. A genuinely oversized or unavailable chain can be renewed inside Chat settings. The signed-in user must write the current task, applicable restrictions and revocations and explicitly confirm replacement. This retires old proposals and folder grants, preserves the mode, history and execution ceilings, and requires a fresh request. Unlimited history is not promised. Optional observations can be omitted only with markers, and material missing facts require `insufficient_evidence`. The provider independently enforces its 60 KiB total wire limit. Recognizable literal credentials stop mandatory input or omit optional observations; this conservative pattern check is not a general secret-discovery guarantee. No credential store is consulted for review evidence.

`src/approval_files.py` can inspect a directly declared simple native shell script operand, such as `python3 job.py`, within existing request filesystem roots. It uses bounded no-follow regular-file reads, supplies at most 8 KiB of complete UTF-8 content as untrusted evidence, and seals/rechecks content hash and file identity. Missing, oversized, inaccessible or unsupported script observation stops Auto. It never executes a script or grants a read outside current roots. External backends cannot be assessed using unrelated local files.

Complex shell expressions, transitive script imports, dynamically selected files and remote script bodies have no complete dependency snapshot. The reviewer must return insufficient evidence when those unresolved facts matter. Ordinary native filesystem bindings still seal path/object identity rather than every byte of file contents; this is not an atomic filesystem snapshot. In-place mutations after the last check and arbitrary program dependencies remain runtime limitations, not guarantees supplied by semantic review.

Private turns retain exact asks and human action evidence only in a process-local cache scoped to the SQL factory, authenticated owner, chat and submission. Request-scoped store instances share that volatile namespace. Linked submission IDs and ask digests persist; private asks and human decisions do not. The cache is bounded to 1,024 entries and 2 MiB per SQL factory, with a one-hour chat-idle TTL (fresh private turns refresh retained evidence), and deletion/rename clears affected evidence. Active follow-ups can use the complete retained chain. Restart, another application worker, eviction or expiry can make earlier private evidence unavailable; Auto then stops explicitly, rather than reconstructing it from a transcript. Always Ask remains available. A private review is admitted only by its recorded process owner. Known multi-worker configurations (`WEB_CONCURRENCY`, `UVICORN_WORKERS`, spawned workers or advertised Gunicorn) block private Auto early; an unadvertised process change is detected by a fresh per-process nonce before a new private turn can supersede work or infer. This is admission, not load-balancer affinity or shared memory. In-process renewal restores only the user’s new statement; missing old asks remain missing. Imported/legacy history, compaction summaries, repeated scheduled instructions, worker claims and arbitrary `AGENTS.md` files are never promoted to authenticated user grants. Active project/thread instruction inheritance and worker/root delegation evidence are not supported inputs to this review envelope; omissions say so. Unavailable earlier context requires a new chat with explicit instructions or Always Ask, not invented consent.

## Grant lifecycle and activity

The existing `ToolApprovalStore` remains the sole grant owner. Proposals bind exact arguments, action effects, owner/chat/run/submission, original request, authorization snapshot, policy, expiry and resource identities. New cards offer only `approve_once` and `deny`. At most one primary and one qualified fallback attempt are reserved per proposal; one final allowed assessment consumes it, and one locked claim permits execution. A human response cannot consume an Auto proposal before or during its independent review. Auto outcomes do not enter the human-authorization journal.

Authorization context and declared script content are revalidated after the provider await and when consuming/claiming the grant. The canonical dispatcher also rechecks tool restrictions, resource/backend identity, browser state, elevation and current turn before dispatch. Owner changes, supersession, cancellation, expiry, changed resources and policy/ceiling changes invalidate old results. Changing a mode or ceiling back does not restore a retired grant. No model result can supply missing execution authority.

The existing Decisions activity pane shows a concise source, disposition, risk, authorization, usage and fixed reason by default. Its native Review details disclosure retains provider/model, fallback cause, policy and reported distributions without crowding each row. It retains prompt/policy version, known/null usage and redacted evidence counts. Sources distinguish Jev, conversation-model fallback, human, YOLO and deterministic paths. Approval activity includes the actual provider/model, fallback cause and separate attempt usage; sanitized captures continue to omit provider labels. Records without the new assessment remain readable as unavailable/legacy; bypassed actions are unassessed, never labeled AI-reviewed. Activity contains no raw asks, paths, arguments, tool output or free-form model rationale. Observation failures do not alter authorization or usage accounting. The service-worker revision refreshes the changed module without deleting user storage.

## Reference behavior and validation limits

The risk/authorization distinction and category policy were independently adapted from the source-audited OpenAI Codex Guardian baseline `5fd36fc5502136160a28a6bebec3590b0df9179a`. Codex's synchronous completion trusts its returned outcome and permits outcome-only parsing defaults; this implementation deliberately requires every Jev distribution and applies the matrix in the host. No upstream code or prompt text is vendored into the product.

Codex also has adaptive trajectory scoring: a binary high/low classification can support a recent-score shortcut, subject to authorization fingerprints, freshness, ordering, coverage and retry/escalation gates. That is not an action-specific safety probability. This port is synchronous and has no adaptive cache, broad prefix trust, remembered MCP allowance or low-score bypass. Those would require separate confinement, cache-validity and policy semantics plus explicit qualification.

Offline tests use real SQL, complete mocked provider transports, the canonical grant/dispatch path and synthetic classifications. They cover the matrix, policy vetoes, response validation, context budget/provenance, revocation, concurrency, readiness and resource changes. They do not measure production Jev judgment, verify a live provider or qualify OS/browser containment. Existing readiness screenshots document the earlier isolated component fixture, not a newly deployed application. No paid provider campaign or deployment is part of this change.

## Explicit review-context renewal

`src/approval_recovery.py` owns metadata-only readiness and user-confirmed renewal through `routes/chat_automation_routes.py`. `GET /api/session/{id}/approval-context` supplies the owned head, policy revision and process challenge; `POST` requires those exact values, a nonblank statement up to 8,000 UTF-8 bytes, a privacy choice and `replace_prior_context=true`. It rejects internal-tool/delegated credentials and requires same-origin browser transport in addition to normal owner authentication. These checks distinguish known tool/API callers from the existing interactive user control channel; they do not claim physical-human attestation from HTTP headers. Neither a chat message, model summary nor imported history can call this mutation as user consent.

The existing SQL feature settings contain only a server-written checkpoint marker. The checkpoint row is a completed, authenticated user submission; old history stays and the review chain stops only at that exact validated marker. Owner-row serialization, head/revision CAS, fresh process challenge, ask digest and owned-row coverage detect stale/tampered replacements. Policy revision changes invalidate pending, in-flight and consumed grants; actual started effects cannot be undone. No approval or elevation is created. Private statements/decisions remain volatile, including renewal, with metadata/digests only in SQL. Forks copy preferences without checkpoint/process metadata or authority.

Sensitivity inspection permits only exact public documentation placeholders such as `api_key=example`, `YOUR_API_KEY` and `<password>`. It does not whitelist arbitrary key-shaped strings, remove fields, redact an action into approval, or fetch secret stores. Nested serialized JSON is parsed with duplicate-key/nonfinite rejection and a finite depth bound; credential-bearing or ambiguous material stops review and offers renewal without exposing the value. This is a conservative egress check, not general DLP. A replacement must preserve the meaningful task/effects/restrictions while excluding secret values; the user, not a model, decides what supersedes earlier review instructions.

Known incompatible selected bindings pause further review admission for up to five minutes in bounded process memory. The memo is scoped to database/owner/chat, saved selection, exact model/registration/auth revision and the reviewed contract version. It caches no approval, denial or uncertainty and does not release usage holds. HTTP failure, refusal and truncation do not become cached policy verdicts. Readiness performs no live probe; expiry permits an explicit future request, not an automatic retry. Structured-output fields are emitted only for the supported exact provider/model contracts; generic APIs and subscription Responses retain strict JSON text validation. Provider contracts are offline compatibility assumptions, not live authentication, model quality or safety calibration.
